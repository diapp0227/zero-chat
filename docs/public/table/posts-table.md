# DynamoDB テーブル定義: `zero-chat-posts`

タイムラインの投稿を保存するテーブル。返信は投稿の項目の中にリストで持つ。
投稿の項目のほかに、投稿の番号を数えるための項目が 1 つだけある ([下記](#投稿の番号を数える項目))。

## テーブル

| 項目 | 値 |
|---|---|
| テーブル名 | `zero-chat-posts` |
| リージョン | `ap-northeast-1` (東京) |
| パーティションキー | `id` (数値) |
| ソートキー | なし |
| キャパシティモード | オンデマンド |

## グローバルセカンダリインデックス (GSI)

| インデックス名 | パーティションキー | ソートキー | 射影 | 用途 |
|---|---|---|---|---|
| `feed-postedAt-index` | `feed` (文字列) | `postedAt` (文字列) | すべて | 全投稿を新しい順に取る |
| `category-postedAt-index` | `category` (文字列) | `postedAt` (文字列) | すべて | 1 つの種類の投稿を新しい順に取る |

## 項目 (投稿 1 件) の属性

| 属性 | 型 | 必須 | 説明 |
|---|---|---|---|
| `id` | 数値 (N) | ○ | 投稿を見分ける一意な番号。テーブルのパーティションキー |
| `feed` | 文字列 (S) | ○ | 常に `"ALL"`。`feed-postedAt-index` のキー |
| `category` | 文字列 (S) | ○ | 投稿の種類。`category-postedAt-index` のキー (値は下の表) |
| `postedAt` | 文字列 (S) | ○ | 投稿日時。UTC の ISO 8601 形式 (例: `2026-10-14T09:00:00Z`)。両インデックスのソートキー |
| `text` | 文字列 (S) | ○ | 本文 |
| `author` | マップ (M) | ○ | 投稿した人 (下の表) |
| `replies` | リスト (L) | - | 返信の一覧。表示する順に並べる。返信がなければ省略するか空のリスト |

`feed` / `category` / `postedAt` のどれかが欠けている、または文字列でない項目は、
インデックスに載らないため API の結果に出てこない。

### `category` の値

Flutter の `PostCategory` の enum 名をそのまま使う。

| 値 | 画面での名前 |
|---|---|
| `announcement` | お知らせ |
| `dailyReport` | 日報 |
| `selfStudy` | 自己学習 |

### `postedAt` を文字列にしている理由

ISO 8601 形式で、桁数とタイムゾーン (`Z` = UTC) を揃えた文字列は、
**文字列として並べた順と日時の順が一致する**。そのためソートキーにそのまま使える。
タイムゾーンや桁数が混ざると順番が崩れるので、必ず UTC の同じ形式で入れる。

### `author` (マップ)

| 属性 | 型 | 説明 |
|---|---|---|
| `id` | 数値 | 人を見分ける番号。投稿作成 API・返信作成 API で作ったものは `0` |
| `userId` | 文字列 | 投稿・返信をした人の Cognito の `sub` (`zero-chat-profiles` のキー)。API で作った投稿・返信にだけある。API のレスポンスには含めない |
| `name` | 文字列 | 名前 |
| `role` | 文字列 | 役割 (例: エンジニア) |
| `color1` | 文字列 | アバターのカラー1 (`#RRGGBB`)。API で作った投稿・返信にだけある (作ったときのプロフィールの色) |
| `color2` | 文字列 | アバターのカラー2 (`#RRGGBB`)。`color1` と同じ |

- 作成 API は、トークンの `sub` を `userId` に入れ、そのときの名前・役職・カラーもコピーして入れる
- 取得 API (`GET /posts`) は、`userId` で `zero-chat-profiles` を読み、**最新の**名前・役職・カラーで上書きして返す。
  そのため、プロフィールを変えると過去の投稿・返信の表示も変わる (投稿テーブルは書き換えない)
- コピーしてある値は、`userId` がない投稿・返信や、プロフィールが見つからない人の表示に使う
- `color1`・`color2` がない項目 (手で入れた投稿など) は、アプリが `id` から決めた色で表示する

### `replies` の要素 (マップ)

| 属性 | 型 | 説明 |
|---|---|---|
| `id` | 数値 | 返信を見分ける番号。**投稿の中で**一意 (返信作成 API は、その投稿の返信の番号の最大値 + 1 を付ける) |
| `author` | マップ | 返信した人 (形は `author` と同じ) |
| `text` | 文字列 | 本文 |
| `repliedAt` | 文字列 | 返信日時。`postedAt` と同じ形式 |

返信を別のテーブルにせず投稿の中に持っているのは、今の画面では返信を投稿と一緒に表示するだけなので、
1 回の読み取りでまとめて取れるほうが簡単なため。
DynamoDB の 1 項目は最大 400 KB なので、返信が非常に多くなる場合は別の項目に分ける。

## 投稿の番号を数える項目

投稿作成 API ([lambda/create-post.md](../lambda/create-post.md)) が、新しい投稿の `id` を決めるために使う項目。
テーブルに 1 つだけ置く。

```json
{ "id": 0, "lastPostId": 10 }
```

| 属性 | 型 | 説明 |
|---|---|---|
| `id` | 数値 (N) | 常に `0`。投稿の番号は 1 から始まるので、投稿とはぶつからない |
| `lastPostId` | 数値 (N) | 最後に付けた投稿の番号。投稿を作るたびに `ADD` で 1 増える |

- `feed` / `category` / `postedAt` を持たないので、どのインデックスにも載らず、API の結果 (タイムライン) には出ない
- 作るときの `lastPostId` は、その時点の投稿の `id` の最大値にする。
  小さいと新しい投稿の番号が既存の投稿とぶつかり、作成に失敗する (上書きはされない)
- 投稿を手で追加するときも、`id` はこの値より大きくしないと、後で API の投稿とぶつかる。
  手で追加したら `lastPostId` もその `id` に合わせる

## 項目の例

```json
{
  "id": 2,
  "feed": "ALL",
  "category": "dailyReport",
  "postedAt": "2026-10-14T09:00:00Z",
  "text": "今日はチームでコードレビュー。\n小さな改善を積み重ねる時間が、プロダクトの強さにつながる。",
  "author": { "id": 2, "name": "いぬ", "role": "エンジニア" },
  "replies": [
    {
      "id": 3,
      "author": { "id": 5, "name": "くま", "role": "エンジニア" },
      "text": "意図まで共有するの、大切ですね！",
      "repliedAt": "2026-10-14T09:15:00Z"
    }
  ]
}
```

## Flutter のモデルとの対応

| DynamoDB | Flutter (`lib/domain/models/`) |
|---|---|
| 項目 (投稿) | `Post` |
| `id` | `Post.id` |
| `author` | `Post.author` (`Author`) |
| `category` | `Post.category` (`PostCategory.values.byName(...)` で変換) |
| `text` | `Post.text` |
| `postedAt` | `Post.postedAt` (`DateTime.parse(...)` で変換) |
| `replies` | `Post.replies` (`List<Reply>`) |
| `replies[].repliedAt` | `Reply.repliedAt` |
| `feed` | なし (DynamoDB の検索用。API のレスポンスにも含めない) |

## TODO: 投稿の `id` を UUID にする

今は `id` を数値の連番にしていて、投稿作成 API が「投稿の番号を数える項目」(`id: 0`) で番号を付けている。
これを、サーバーで作る **UUID (文字列)** に変えたい。

### 変えたい理由

- 番号を数える項目がいらなくなり、投稿の作成が書き込み 1 回で済む (今は番号の更新と保存の 2 回)
- すべての投稿の作成が番号の項目 1 つに集中しなくなる (1 項目あたりの書き込みの上限を気にしなくてよい)
- 番号の項目の `lastPostId` を、手で追加した投稿に合わせる手間と、合わせ忘れて番号がぶつかる心配がなくなる
- 連番だと投稿の総数やほかの投稿の `id` を推測できるが、UUID なら推測できない

タイムラインの並び順は `postedAt` のインデックスで決めているので、`id` が連番でなくなっても並び順は変わらない。

### やること

1. **DynamoDB**: パーティションキーの型は後から変えられないので、`id` を**文字列 (S)** にした新しいテーブルを作る
   (インデックス 2 つも同じ定義で作る)
2. **データの移行**: 既存の投稿を新しいテーブルにコピーし、`id` を UUID に振り直す。番号を数える項目 (`id: 0`) は移さない
3. **Lambda (作成)**: `_next_post_id` をやめて `str(uuid.uuid4())` で `id` を作る。
   権限から `dynamodb:UpdateItem` を外し、`PutItem` だけにする
4. **Lambda (取得)**: `_to_json` の数値の変換は `id` には使わなくなる。レスポンスの `id` が文字列になる
5. **Flutter**: `Post.id` を `int` から `String` に変え、`HttpPostRepository` の変換、`FakePostRepository` の番号の付け方、テストを直す
6. **ドキュメント**: このファイル、[lambda/create-post.md](../lambda/create-post.md)、[lambda/get-posts.md](../lambda/get-posts.md) の `id` の型と例を直す
7. 新しいテーブルに切り替えたら、古いテーブルを削除する

### あわせて決めること

- 返信の `id` (`replies[].id`) も UUID にそろえるか (今は投稿の中で「最大値 + 1」の数値)
- 投稿した人は、すでに `author.userId` (Cognito の `sub`) で見分けている。`author.id` (常に `0`) はなくしてよい
- 古いアプリは `id` を数値として読むので、API を切り替えると投稿を読めなくなる。
  API とアプリ (Web 版・iOS など) を切り替える順番とタイミングを決めておく
